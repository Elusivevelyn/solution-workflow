# 文字方案设计

## 输入

读取项目需求、行业调研笔记、方案建设方向与模块框架，以及 SHARE 和项目内相关产品、技术资料。若用户要求直接继续已有方案，先读取最新文字稿，避免重复研究或覆盖手改内容。

## 设计推进

1. **主动回读研究材料。** 开始第二章前，完整回读最新行业调研笔记及人工填写内容，同时读取建设方向文档中的内部调研结果。结合已确认范围，直接将可用的业务做法、功能细节、实现条件和用户要求保留的内容用于方案设计，不先建立分类清单或只凭方向标题展开。
2. **先设计第二章。** 在 `03_文字方案/文字方案.md` 建立总体骨架，先写业务与价值，用典型任务说明平台使用过程和改善的环节，再落实总体架构、共用底座及具体模块。逐模块设计时，利用本轮回读形成的完整认识；缺少某个具体做法或条件时回查原文，不每写一个模块就重读全部文件。
3. **完善第一章和第四章。** 从行业笔记、已确认问题及第二章设计中提取行业现状、建设必要性与目标，形成第一章；按方案范围写建设阶段、阶段成果、适用的 PoC 和合作分工，形成第四章。第三章按下表现有规则编写。最终文稿按第一至第四章顺序组织。
4. **随设计写回并确认。** 对照需求、研究依据和建设范围，处理影响方案的遗漏、重复、层级混乱或无依据承诺；检查架构与模块一致、建设路径及 PoC 对应实际内容。直接修正文稿，不另做检查报告，经讨论确认形成文字定稿。

以上按讨论进度逐步写回同一文字方案，不一次生成全部环节。用户已确认部分保留；新资料影响既有方向时提出影响，与用户讨论，不擅自改写范围。

## 第二章的内容分工与深度

| 内容 | 写作动作 | 完成标准 |
| --- | --- | --- |
| 业务与价值、典型任务 | 以角色开展任务的过程串起操作、系统响应和结果，说明现有做法得到改善的具体环节；将研究中适用的流程和细节纳入本项目 | 读者能够理解谁怎样使用、处理完得到什么，以及改善在哪里 |
| 总体架构 | 将支撑这些任务的角色入口、业务模块、共用服务和数据组织成架构，说明关键连接对应的调用、流转或依赖 | 模块与后文建设内容一致，层级和连接具有实际含义 |
| 共用底座建设 | 说明需要建设或整合的共用资源、功能和数据，列明形成的成果及使用这些成果的模块 | 每项建设有具体产出和使用方，能够与架构概览区分 |
| 具体业务模块 | 从业务目标落到直接作用，再写支撑该作用的关键功能和使用过程，补充会影响方案成立的依赖条件 | 商机阶段能够说明使用者、处理动作、结果和关键条件；参数、接口细节和验收指标按项目需要展开 |

同一信息在承担该职责的位置展开，其他位置保留理解关系所需的简短引用。不要把价值、架构和底座都写成一组重复的能力名称。研究内容应转化为本项目的业务和建设设计，保留必要出处，不在正文堆积资料摘录。

## 默认四章及职责

| 章节 | 内容职责 |
| --- | --- |
| 背景与目标 | 行业背景、客户需求、建设必要性、方案定位；定位衔接需求与建设方案 |
| 解决方案 | 总体架构、共性底座、分模块建设内容、典型应用和业务流程 |
| 产品能力与实践 | 按产品独立介绍，突出相关优势、功能及有依据的实践案例 |
| 建设与交付 | 建设阶段、任务成果、适用的 PoC 设计、合作方式与分工 |

产品章节集中介绍产品，建设模块仍需说明必要的技术支撑和依赖关系，但不要在每个模块重复产品宣传。缺少实施计划或 PoC 依据时讨论建议，不编造既定工期、验收指标或合作承诺。

## 输出与边界

输出完整文字方案，保留必要的来源定位或材料引用，以便后续查证技术能力。此时不为了 PPT 页数提前删掉必要逻辑，也不提前绑定页面布局。

用户确认完整方案后，将定稿交给 [页面原型子 Skill](../solution-page-prototype/SKILL.md)。确认不要求额外复制一份定稿文件，可在现有文稿中注明定稿并以其为内容基准。
