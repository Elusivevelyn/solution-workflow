# 内部资料与建设方向

## 输入

- 项目需求说明、最新行业调研笔记及用户当前讨论。
- 必须实际检查并读取 `C:/evelyn/RAYS/Evelyn/Solution-Knowledge/REFERENCE/SHARE` 中的公司产品能力资料。用户直接放入文件，不要求另建索引、填写数据库或先改成统一格式。
- 项目 `02_内部调研与建设方向/` 下按需提供的历史方案、产品和技术资料。

## 对内调研

1. 建立公司整体产品认知，深入读取与候选方向有关的产品功能、说明和案例。只列出文件名不算读取。PPT 视觉模板留待制作环节分析，不将其当成能力证据。
2. 针对外部调研中有价值的方向，结合内部功能和案例，说明公司能否实现、现有功能如何组合完成，以及自身能力能否在原方向上扩展出更好的效果。写到功能和实现过程，避免只列产品名或给出“支持”结论。
3. 将上述判断、实现细节和资料出处直接保留在 `02_内部调研与建设方向/方案建设方向与模块框架.md` 的相关方向下。内部资料启发的新方向也写入该文档。无需另建内部调研报告，不强制给能力分级；影响成立与否的接入、数据或技术条件随具体内容说明。
4. 让表述与资料证据相符。内部资料未说明的能力或扩展效果标明为设想及其依据，不虚构性能和案例。

内部项目、技术资料可提示用户按需补充；未提供时正常推进，不增加强制确认节点。SHARE 为空或产品文件无法读取时，明确暂缺能力依据，仍可讨论行业候选方向；不能声称已完成公司能力验证，也不能无依据确定为公司既有能力。用户随后放入资料时重新读取并修正相关判断。

## 回答问题并确认方向

1. 综合内外调研，回到需求说明中的待研究事项，写出影响方案的结论、依据和仍成立的假设。能够从现有资料回答的直接回答，只有必须由用户决定的取舍才提问。把相关行业现状、问题及建设必要性的资料依据一并保留，供第一章使用。
2. 提出建设方向，写明所改善的业务环节、我方介入方式、直接价值、能力依据和大致范围。按项目需要形成模块骨架，方向可以并列、递进或相互支撑，不强制独立成案或给关系定性。
3. 与用户讨论取舍后写回同一建设方向文档，保留支撑判断的内部实现材料及外部出处。候选内容与已确认范围在文字中明确，不把讨论设想自动转成建设承诺。

## 输出与交接

在 `02_内部调研与建设方向/方案建设方向与模块框架.md` 保存讨论成果，内容包括：

- 经研究确认的问题、业务场景及方案主线。
- 主要建设方向和模块、业务价值、大致范围及实际影响设计的关系。
- 各方向的内部实现方式、扩展构想及来源，和行业笔记中相关做法的出处。
- 影响方案成立的条件、待定或可选内容，以及用户已作出的取舍。

用户确认后，将该文件、需求、完整行业笔记和相关产品资料交给 [文字方案子 Skill](../solution-written-plan/SKILL.md)。建设方向文档保留内部调研结果，不能替代文字方案阶段对行业笔记的主动回读。无需额外创建决策台账。
