# 生成前诊断与方案产物模板

在新建或大幅迭代客户方案、方案文字架构、PPT 内容架构或最终 PPT 时读取本文件。

本文件提供结构，不要求机械填满所有字段。只保留会影响当前项目判断的内容。

## 一、生成前诊断输出顺序

生成前先向用户返回以下内容：

1. 当前任务理解；
2. 方案生成前置诊断表；
3. 最高影响的 3—5 个补充问题；
4. 若直接继续，将采用的临时假设与表达边界；
5. 当前准备度判断。

默认在此暂停。用户明确要求诊断后直接继续时，可展示后在同一轮继续。

## 二、当前任务理解

用简短语言说明：

- 当前客户与项目；
- 当前项目阶段；
- 用户要求的交付物；
- 正在沿用或修改的版本；
- 最新反馈指向的变化；
- 当前理解的汇报目的；
- 当前理解的主要受众。

未确认内容必须写成“暂定理解”，不得写成确定事实。

## 三、方案生成前置诊断表

使用以下字段：

| 检查问题 | 已获得的信息 | 状态 | 来源 | 缺失或冲突影响 | 如直接继续的处理方式 |
|---|---|---|---|---|---|
| 本次汇报要推动什么 |  |  |  |  |  |

状态仅使用：

- **已满足**：存在明确且可定位的输入；
- **部分满足**：已有方向，但不足以直接支撑判断；
- **未获得**：当前 Reference 中没有找到；
- **存在冲突**：不同有效资料不一致；
- **当前不适用**：受项目阶段或交付物类型影响，本轮无需回答。

“来源”尽量定位到文件、页码、幻灯片、章节或反馈日期。

“如直接继续的处理方式”只能采用以下方式之一：

- 使用明确标记的临时假设；
- 保持开放表达；
- 缩小本轮输出深度；
- 转为待确认项；
- 不进入客户正文；
- 并列保留冲突，等待确认。

## 四、检查问题库

### A. 项目与需求

- 客户和项目背景是否明确；
- 客户明确提出的问题和需求是什么；
- 项目建设目标是什么；
- 当前项目阶段是什么；
- 用户、业务场景和关键流程是否明确；
- 当前边界、约束和已知依赖是什么；
- 当前确认的交付范围和结果是什么。

### B. 本次汇报任务

- 本次要求交付什么；
- 本次汇报要推动什么判断、共识、决策或行动；
- 谁是主要听众、谁参与决策；
- 主要听众真正关心什么、可能质疑什么；
- 客户当前已经理解或接受什么；
- 希望客户最终记住什么；
- 本轮明确不解决什么；
- 哪些内容必须保留、避免或弱化。

### C. 解决方案机制

- 谁在什么场景使用；
- 用户从哪里开始、经过哪些步骤、最终得到什么；
- 平台在每个环节分别做什么；
- 业务、数据和服务怎样形成闭环；
- 方案需要处理哪些核心对象；
- 最终输出什么方案、服务、数据、任务或结果；
- 解决机制与客户价值之间的因果是否成立。

### D. 技术证明与能力边界

- 每项关键技术为什么需要；
- 技术分别支撑解决方案的哪个环节；
- 输入、处理、输出和协同关系是否明确；
- 哪些是已有明确能力；
- 哪些需要定制、验证、合作方或客户侧资源；
- 外部系统、数据、接口和部署条件是什么；
- 当前阶段需要讲到什么深度；
- 最终技术交付物是否明确。

### E. PPT 与制作条件

- 是沿用现有 PPT 还是重构；
- 最新有效版本是哪一个；
- 最新 feedback 是什么；
- 是否存在必须使用的 PPT 模板；
- 页面数量、汇报时长和会议形式是否有限制；
- 哪些历史页面必须保留、删除或重写；
- 是否有案例、图片、截图、演示或其他证据资产。

不要把所有缺失项都变成提问。优先提问会改变汇报目的、解决方案主线、技术职责或交付范围的问题；其他缺口保留在表格中。

## 五、准备度结论

不得只给一个百分比或总分。使用判断性结论，例如：

> 当前资料足以形成内部解决方案和初版 PPT 架构，但主要听众和本次要推动的客户判断尚未完全明确，可能改变业务与技术内容的权重。建议优先确认这两项；首期范围可暂列为待确认，不影响先形成前期交流方案。

准备度结论至少回答：

- 当前能否开始；
- 最适合先产出到哪一层；
- 哪些缺口可能改变主线；
- 哪些缺口可以带着边界继续；
- 如果继续，采用什么临时处理。

## 六、用户补充后的处理

用户回答后：

1. 更新任务理解和对应诊断项；
2. 区分确认信息、暂定选择和仍未解决的问题；
3. 只追问仍会实质改变结果且无法合理处理的事项；
4. 用户确认继续后，不因低影响缺口重复阻塞；
5. 将未解决项带入后续产物的假设和边界字段。

## 七、解决方案机制表

| 客户问题 | 用户 / 角色 | 场景与触发 | 输入 | 用户 / 业务流程 | 平台介入与协同 | 输出结果 | 闭环关系 | 客户价值 | 事实 / 假设 / 待确认 |
|---|---|---|---|---|---|---|---|---|---|
|  |  |  |  |  |  |  |  |  |  |

完成后检查：

- 是否讲清用户怎样使用，而非只列功能；
- 是否讲清业务怎样运行，而非只列模块；
- 是否存在开始、过程、结果和后续反馈；
- 各能力是否共同完成一个结果；
- 业务价值是否能够追溯到解决机制；
- 是否把未确认建设范围包装成确定方案。

## 八、解决机制—技术证明映射表

| 解决方案环节 | 为什么需要技术支撑 | 技术职责 | 输入 | 处理 | 输出 | 与其他能力协同 | 能力状态 | 定制 / 外部 / 客户条件 | 技术交付结果 | 来源与边界 |
|---|---|---|---|---|---|---|---|---|---|---|
|  |  |  |  |  |  |  |  |  |  |  |

检查：

- 是否存在脱离解决方案环节的技术；
- 是否把产品名称当成技术职责；
- 是否解释了为什么需要这项技术；
- 是否说明技术之间如何协同，而非平行罗列；
- 是否区分现有能力、项目定制和外部依赖；
- 是否明确最终形成什么结果或交付物。

## 九、客户认知链

先用自然语言写一遍，不使用 PPT 标题：

> 客户先要明白 ______；随后意识到 ______；因此接受 ______；再通过 ______ 相信方案能够实现；最后愿意 ______。

然后记录：

- 当前认知；
- 目标认知；
- 1—3 个核心判断；
- 必要的认知节点；
- 每个节点的前置关系；
- 哪些属于主线、支撑和内部分析。

## 十、章节契约表

| 章节 | 进入前认知 | 本章回答的问题 | 本章说服任务 | 必须包含 | 不回答 / 不提前展开 | 结束后认知 | 对下一章的承接 |
|---|---|---|---|---|---|---|---|
|  |  |  |  |  |  |  |  |

章节名称和数量由当前项目决定，不套用固定模板。

## 十一、页面任务表

| 页序 | 章节 | 客户可见标题 | 页面任务 | 隐藏结论 | 为什么此时需要 | 前置依赖 | 后续承接 | 新增认知 / 信息增量 | 必要内容与证据 | 主线 / 支撑 / 附件 | 来源、状态与边界 | 历史页处理 |
|---|---|---|---|---|---|---|---|---|---|---|---|---|
|  |  |  |  |  |  |  |  |  |  |  |  |  |

隐藏结论统一写成：

> 讲完这一页，我希望客户得出：______。

如果删除一页后，客户没有缺少新的认知，则该页不应独立存在。优先重新定义、移动、合并或删除。

## 十二、假设与待确认清单

用户允许在资料不完整时继续后，保留：

| 项目 | 当前处理 | 对方案的影响 | 客户正文表达方式 | 后续确认方式 |
|---|---|---|---|---|
| 临时假设 / 待确认 / 冲突 |  |  |  |  |

临时假设不得在后续页面或视觉制作中转化成客户确认事实。
