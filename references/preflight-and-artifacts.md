# 生成前诊断与方案产物模板

在新建或大幅迭代客户方案、方案文字架构、PPT 内容架构或最终 PPT 时读取本文件。

本文件提供结构，不要求机械填满所有字段。只保留会影响当前项目判断的内容。

## 项目状态与增量读取记录

首次 customer、product 建立的依据应可在后续恢复。每次交付在 `03_solution-history` 保存版本内容，并维护一份项目状态记录（如 `project-state.md`），不要求用户手工维护多套表。该记录是依据索引与工作状态，不是新的客户原始材料。

至少保留：

- **输入基线**：已读取的 customer、product 文件及版本、来源位置、已提取的准确事实或摘录、条件和未覆盖范围；默认未更新，不为检查是否更新反复扫描或计算文件 Hash。
- **当前需求与能力**：初始要求、来源、能力主状态、边界、假设和待确认项；后续需求更新关联具体 feedback，保留被替代内容的沿革。
- **当前方案**：当前工作版本、生成 / 待审核 / 已确认等状态、文件位置、机制与章节结论；不得把生成稿作为事实证据。
- **反馈处理进度**：反馈来源及条目、目标版本、是否已处理或被替代、造成的增删调整、产出版本；旧反馈仍有效的约束继续保留。
- **可复用研究**：来源、日期、结论、适用条件和未解决问题；任务或时效发生变化时只核验相关部分。

后续读取顺序为本轮 feedback → 对应版本与项目状态 → 受影响内容和已有证据。只有用户告知原始资料更新，或已有记录确实不能支持本轮判断时，才定点补读 customer、product，并说明原因。上下文丢失时先读项目状态；缺少状态记录时从对应版本的来源记录恢复，不用模型记忆猜测原始事实。

反馈应按以下关系处理，可并入已有反馈回退记录，不另造重复表格：

| 反馈条目及目标版本 | 性质与来源身份 | 替代 / 保留的旧要求 | 内容增删或表达修改 | 受影响机制及技术 | 复用依据 / 必要补读 | 新版本及处理状态 |
|---|---|---|---|---|---|---|
|  | 新需求 / 确认事项 / 方案调整 / 表达意见 / 能力主张 |  |  |  |  |  |

首次 history、feedback 为空记为“当前不适用”，不要求补齐；模板不存在或用户未指定时按当前输出需要处理。用户明确排除的文件不参与基线与优先级判断，测试残留内容不能污染首次输入。

## 一、生成前诊断输出顺序

生成前先向用户返回以下内容：

1. 当前任务理解；
2. 方案生成前置诊断表；
3. 优先不超过 3—5 个、只能由用户补充的高影响问题；没有必要问题时不凑数；
4. 若直接继续，将采用的临时假设与表达边界；
5. 当前准备度判断。

默认在此暂停。用户明确要求诊断后直接继续时，可展示后在同一轮继续。

首轮诊断可以早于完整研究，但必要时先核验客户主体；将公开可查的问题列为 Codex 的研究动作，不直接要求用户代查。获准继续后先完成必要研究或有效复用，再形成机制；已有继续授权时不为研究记录新增确认关卡。

## 二、当前任务理解

用简短语言说明：

- 当前客户与项目；
- 当前项目阶段；
- 用户要求的交付物；
- 正在沿用或修改的版本；
- 最新反馈指向的变化；
- 当前理解的汇报目的；
- 当前理解的主要受众。

材料接收者、最终交流对象、实际使用者与建设 / 购买方分别标明；可兼任角色，未知具体人员时不编造。初步说明客户需要、受众已知 / 未知及本次希望帮助形成的判断，后续研究和机制可校正这份理解。

未确认内容必须写成“暂定理解”，不得写成确定事实。

首次没有历史版本或反馈时直接注明，不凑出一份历史基线。反馈迭代只更新变化项和受影响的诊断，不把这份模板理解为重新审阅全库的命令。

## 三、方案生成前置诊断表

使用以下字段：

| 检查问题 | 已获得的信息及主张性质 | 状态 | 来源与身份 | 缺口类型 | 缺失或冲突影响 | 研究动作 / 继续处理 |
|---|---|---|---|---|---|---|
| 本次汇报要推动什么 |  |  |  |  |  |  |

状态仅使用：

- **已满足**：存在明确且可定位的输入；
- **部分满足**：已有方向，但不足以直接支撑判断；
- **未获得**：目前没有获得，注明“尚未研究”“核验后未找到”或“受限无法核验”，三者不能混同；
- **存在冲突**：不同有效资料不一致；
- **当前不适用**：受项目阶段或交付物类型影响，本轮无需回答。

“已满足”表示当前问题有足够依据，不表示其中所有推断都是客户确认事实。来源与主张性质分开，沿用主 Skill 的边界，不用一个“确认”标签覆盖整份文件。

“缺口类型”用于分配动作：

- **可公开查证**：由 Codex 核验主体、查阅官方来源或复用现有研究，记录实际结果；
- **需项目确认**：目标、预算、审批、内部系统或具体受众认知等公开来源不能证明的信息，按影响提问；
- **可暂定处理**：明确假设、开放表达、缩小深度或移出正文，并保留影响。

若不能研究，说明真实权限、保密或工具限制。不得假造研究，不因用户同意继续而省略可执行的必要核验。

“研究动作 / 继续处理”可采用：

- 核验公开信息或引用适用的已有研究；
- 使用明确标记的临时假设；
- 保持开放表达；
- 缩小本轮输出深度；
- 转为待确认项；
- 不进入客户正文；
- 并列保留冲突，等待确认。

### 证据记录（内部）

| 主张 | 主张性质 | 来源主体 / 转述身份 | 原文位置 / 链接 | 资料日期 | 查询或接收日期 | 当前适用性 | 对方案的具体影响 |
|---|---|---|---|---|---|---|---|
|  |  |  |  |  |  |  |  |

公开业务事实、客户明确需求、任务要求、行业信息、方案判断和假设按主 Skill 分类。来源中没写的事实不能自行补全；未知日期注明未标注。合作方转述保留其身份，不降为无用信息，也不升级为客户原文或审批。

### 必需步骤执行记录（内部）

| 必需步骤 | 本轮是否适用及理由 | 实际动作或复用来源 | 结论 / 文件定位 | 未解决问题及下游影响 |
|---|---|---|---|---|
| 客户、行业与项目背景研究 |  |  |  |  |
| 相关角色需要识别 |  |  |  |  |
| 客户需要与方案回应核验 |  |  |  |  |

放在现有内部工作稿或来源记录中即可，不强制另建多份文件，不放进客户正文。研究 / 角色分析应在机制前有依据，需要—回应核验在机制形成后、客户架构前完成。查看实际结论，不能用“已研究”和空表代替。局部修改可以注明复用或不适用理由。

## 四、检查问题库

### A. 项目与需求

- 客户和项目背景是否明确；
- 客户明确提出的问题和需求是什么；
- 项目建设目标是什么；
- 当前项目阶段是什么；
- 用户、业务场景和关键流程是否明确；
- 当前边界、约束和已知依赖是什么；
- 当前确认的交付范围和结果是什么。
- 客户主体是否核验，公开业务、行业环境与本项目背景之间有什么关联；
- 哪些研究已经完成或可复用，哪些只是尚未开展；
- 哪条证据影响了客户需要和建设理由，是否仍属于有依据的判断。

### B. 本次汇报任务

- 本次要求交付什么；
- 本次汇报要推动什么判断、共识、决策或行动；
- 谁是主要听众、谁参与决策；
- 主要听众真正关心什么、可能质疑什么；
- 客户当前已经理解或接受什么；
- 希望客户最终记住什么；
- 本轮明确不解决什么；
- 哪些内容必须保留、避免或弱化。
- 受众当前理解的依据是什么，哪些只是表达起点假设；
- 当前认知任务如何影响方案取舍，而不只是改变讲述顺序。

### C. 解决方案机制

- 谁在什么场景使用；
- 用户从哪里开始、经过哪些步骤、最终得到什么；
- 平台在每个环节分别做什么；
- 业务、数据和服务怎样形成闭环；
- 方案需要处理哪些核心对象；
- 最终输出什么方案、服务、数据、任务或结果；
- 解决机制与客户价值之间的因果是否成立。
- 实际使用者与建设 / 购买方是否不同，其需要和方案回应分别是什么；
- 决策 / 评估角色及合作方的职责和约束有什么依据；
- 是否有证据说明原设想需调整、缩小或不适合当前阶段。

### D. 技术证明与能力边界

- 每项关键技术为什么需要；
- 技术分别支撑解决方案的哪个环节；
- 输入、处理、输出和协同关系是否明确；
- 哪些是已有明确能力；
- 哪些需要定制、验证、合作方或客户侧资源；
- 外部系统、数据、接口和部署条件是什么；
- 当前阶段需要讲到什么深度；
- 最终技术交付物是否明确。

### E. PPT 与制作条件

- 是沿用现有 PPT 还是重构；
- 最新有效版本是哪一个；
- 最新 feedback 是什么；
- 是否存在必须使用的 PPT 模板；
- 页面数量、汇报时长和会议形式是否有限制；
- 哪些历史页面必须保留、删除或重写；
- 是否有案例、图片、截图、演示或其他证据资产。

不要把所有缺失项都变成提问。优先提问会改变汇报目的、解决方案主线、技术职责或交付范围的问题；其他缺口保留在表格中。

## 五、准备度结论

不得只给一个百分比或总分。使用判断性结论，例如：

> 当前可继续做必要研究和候选机制设计。客户公开背景尚待核验，组织建设理由也未获得充分依据，因此暂不能宣称客户针对性已验证；主要受众的具体判断任务需项目确认。首期范围可保留待确认，不阻止前期交流候选方案。

准备度结论至少回答：

- 当前能否开始；
- 最适合先产出到哪一层；
- 哪些缺口可能改变主线；
- 哪些缺口可以带着边界继续；
- 如果继续，采用什么临时处理。

分开评价证据充分度、客户针对性、机制 / 叙事连贯性与文件质量。一项通过不能代替其他项通过。

## 六、用户补充后的处理

用户回答后：

1. 更新任务理解和对应诊断项；
2. 区分确认信息、暂定选择和仍未解决的问题；
3. 只追问仍会实质改变结果且无法合理处理的事项；
4. 用户确认继续后，不因低影响缺口重复阻塞；
5. 将未解决项带入后续产物的假设和边界字段。

缺少建设理由证据但用户允许继续时，明确交付候选稿；不能以“已确认继续”将假设升级成事实。背景、角色需要与认知目标的必要研究或有效复用必须先于机制。

## 七、解决方案机制表

先识别角色需要，再形成机制。实际使用者关注任务、操作成本与结果；建设 / 购买方关注为什么值得投入及业务目标；评估 / 决策角色关注已知职责与判断条件；合作方存在时才记录转述、交付和协同责任。一个主体可兼任角色，不强制四类齐全，不推定个人诉求、采购权或商业动机。

### 角色需要—方案回应映射

| 哪个角色 | 什么需要 / 目标 | 依据与确认程度 | 方案回应机制 | 预期结果及依据 | 仍需确认什么 |
|---|---|---|---|---|---|
|  |  |  |  |  |  |

机制生成前填需要与依据，机制形成后补回应和结果；可与下面机制表合并引用，避免重复记录。使用者的结果不能自动证明购买方值得建设；不能用通用价值口号补齐组织建设理由。

| 客户问题 | 用户 / 角色 | 场景与触发 | 输入 | 用户 / 业务流程 | 平台介入与协同 | 输出结果 | 闭环关系 | 客户价值 | 事实 / 假设 / 待确认 |
|---|---|---|---|---|---|---|---|---|---|
|  |  |  |  |  |  |  |  |  |  |

完成后检查：

- 是否讲清用户怎样使用，而非只列功能；
- 是否讲清业务怎样运行，而非只列模块；
- 是否存在开始、过程、结果和后续反馈；
- 各能力是否共同完成一个结果；
- 业务价值是否能够追溯到解决机制；
- 是否把未确认建设范围包装成确定方案。
- 哪条客户特定证据影响了方案选择；更换客户时哪些判断需改变（允许复用通用结构）；
- 是否分别回应了用户任务与组织建设理由，并说明二者的因果；
- 研究与初步认知目标怎样影响机制取舍；
- 反证是否得到处理，而不是为固定方案补造需要。

## 八、解决机制—技术证明映射表

| 解决方案环节 | 为什么需要技术支撑 | 技术职责 | 输入 | 处理 | 输出 | 与其他能力协同 | 能力状态 | 定制 / 外部 / 客户条件 | 技术交付结果 | 来源与边界 |
|---|---|---|---|---|---|---|---|---|---|---|
|  |  |  |  |  |  |  |  |  |  |  |

检查：

- 是否存在脱离解决方案环节的技术；
- 是否把产品名称当成技术职责；
- 是否解释了为什么需要这项技术；
- 是否说明技术之间如何协同，而非平行罗列；
- 是否区分现有能力、项目定制和外部依赖；
- 是否明确最终形成什么结果或交付物。

## 九、客户认知链

本模板分两次填写但只保留一份：第 1.4 节先形成初步认知目标，机制和技术证明形成后在第五步校正完整认知链。

| 面对的角色 | 客户背景与目标 | 具体问题 / 需要及依据 | 当前理解及依据 / 未知 | 本次要形成的判断 | 需讲清的关系或疑问 | 方案回应与证明 | 对章节 / 页面的约束 |
|---|---|---|---|---|---|---|---|
|  |  |  |  |  |  |  |  |

初步阶段不要为填写后两列提前生成确定机制。研究可以修改暂定理解；已确认目标仍保留其权限边界。官网背景不能证明受众个人认知；未知时标注保守起点、分层解释或可选支撑，只对有实质影响的具体问题澄清。

校正后用自然语言表达，不使用 PPT 标题：

> 基于 ______，受众已知 / 尚待评估 ______；本次需澄清 ______；比较或解释 ______；通过 ______ 评估适用性；最终帮助其形成 ______ 的判断。

保留：

- 当前认知；
- 目标认知；
- 1—3 个核心判断；
- 必要的认知节点；
- 每个节点的前置关系；
- 哪些属于主线、支撑和内部分析。

完整链条必须说明研究和角色分析如何影响机制、内容与顺序，不只证明各表都已填写。结论可以是接受某方向、继续比较、缩小范围或暂不采用原建议，不能把说服购买设为默认终点。

## 十、章节契约表

| 章节 | 进入前认知及来源 / 假设 | 本章回答的问题 | 本章认知任务及对应需要 | 必须包含 | 不回答 / 不提前展开 | 结束后认知 | 对下一章的承接 |
|---|---|---|---|---|---|---|---|
|  |  |  |  |  |  |  |  |

章节名称和数量由当前项目决定，不套用固定模板。

前置认知来自已知沟通或前文已建立的判断。首章不得依赖未论证的共识；客户已经熟悉的背景可以简述，不为表格完整重复公司简介。

## 十一、页面任务表

| 页序 | 章节 | 客户可见标题 | 页面任务及对应角色需要 / 认知任务 | 隐藏结论 | 为什么此时需要 | 前置依赖及依据 | 后续承接 | 新增认知 / 信息增量 | 必要内容与证据 | 主线 / 支撑 / 附件 | 来源、状态与边界 | 历史页处理 |
|---|---|---|---|---|---|---|---|---|---|---|---|---|
|  |  |  |  |  |  |  |  |  |  |  |  |  |

隐藏结论统一写成：

> 讲完这一页，我希望客户得出：______。

如果删除一页后，客户没有缺少新的认知，则该页不应独立存在。优先重新定义、移动、合并或删除。

隐藏结论必须回答受众具体疑问，并追溯至角色需要或认知任务。只复述功能、只证明页面自身完整，不算完成。

## 十二、假设与待确认清单

用户允许在资料不完整时继续后，保留：

| 项目 | 当前处理 | 对方案的影响 | 客户正文表达方式 | 后续确认方式 |
|---|---|---|---|---|
| 临时假设 / 待确认 / 冲突 |  |  |  |  |

临时假设不得在后续页面或视觉制作中转化成客户确认事实。
